# Requirement and use-case traceability matrix

Initial baseline status: **PLANNED**  
This matrix is planning evidence only. No business feature existed when it was created.

Prompt 1 added the build, configuration, Flyway, JPA entity, repository, and database-independent domain-test foundation. Prompt 2 added and tested shared NFR-2 through NFR-4 infrastructure. Program creation and management add UC-P1/UC-P2 and FR-1 through FR-3. Program lifecycle advancement adds UC-P3, FR-4, FR-8.5, and SD-1. Screening preparation adds UC-S1, FR-5, FR-6.3, and AD-3. Screening submission adds UC-S2, FR-6.1/6.2, and SD-2. Assignment and Review add UC-S3, FR-7, and SD-3. Decision, final submission, and conflict-safe scheduling add UC-S4, FR-8.1-FR-8.4, and SD-4. These include user-scoped cross-operation idempotency, required locks, audit, and rollback-path evidence. Those rows remain `IMPLEMENTED`, rather than `VERIFIED`, until their planned real-MySQL transaction and concurrency integration tests are executed.

## Status rules

- `PLANNED`: mapped but no implementation claim.
- `IMPLEMENTED`: code and focused tests exist, but end-to-end verification may remain.
- `VERIFIED`: relevant automated tests have passed in the required profile and evidence is recorded.
- `BLOCKED`: use only with a concrete external blocker and explanation.

Every implementation task must update affected rows with actual class/test names and evidence. Never bulk-promote statuses based on intention.
